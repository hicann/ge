# Ascend C Declarative Address Refresh Custom Operator Offline Sample

## Overview

This offline sample demonstrates AIR/OM generation, serialization and deserialization of custom operator `PortableOp` state, declaration of offline kernel launch metadata and args layout through `AnnotatedArgsOp::DeclareLaunchArgs`, and OM loading and execution through ACL.

Core pipeline:

```text
Compile callback builds the Ascend C kernel with ACL RTC
  -> PortableOp::Serialize/Deserialize saves and restores the shape-to-kernel-binary map
  -> DeclareLaunchArgs declares kernel/bin/block_dim/AnnotatedKernelArgs
  -> ATC writes TaskDef.kernel().args and context.args_format
  -> GE loads and dispatches the custom kernel from TaskDef
  -> ModelArgsManager refreshes INPUT/OUTPUT address slots before execution
```

Key implementation points:

- The operator type is `AnnotatedAddCustom` and it implements `AnnotatedArgsOp`.
- The offline model path does not rely on manually loading and launching the kernel in `EagerExecuteOp::Execute`.
- `DeclareLaunchArgs` annotates the `x1`, `x2`, and `y` address slots with `AnnotatedKernelArgs`.
- The kernel binary is still compiled by the `Compile` callback through ACL RTC and cached by input shape key in the `PortableOp` state.
- `PortableOp::Serialize` and `PortableOp::Deserialize` persist and restore the multi-shape kernel binary map.

## Prerequisites

- CANN has been installed and configured, for example by running `source /usr/local/Ascend/cann/set_env.sh` (adjust the path for your installation).
- The CANN headers and libraries must provide the declarative address refresh APIs, including `AnnotatedArgsOp`, `AnnotatedKernelLaunchInfo`, and `AnnotatedKernelArgs`.
- `atc` is available.
- The environment provides ACL, GE, and Graph headers and libraries.
- `cmake` and `g++` are available.

## Quick Run

Run in `examples/custom_op/annotated_args_refresh_add_custom/offline`:

```bash
bash run.sh
```

The script will:

1. Build `output/op_graph/lib/<os>/<arch>/libcust_opapi.so`.
2. Run `annotated_args_refresh_add_graph_build` to generate `output/single_add.air`.
3. Run `atc` to generate `output/single_add.om`.
4. Run `annotated_args_refresh_add_model_exec` to load and execute the OM.

Expected output includes:

```text
Model executed successfully!
First element of output: 3.000000
```

## Declarative Address Refresh

`AnnotatedAddCustom::DeclareLaunchArgs` in `ge/custom_op.cpp` is the core implementation:

- Gets input and output tensor logical addresses from `AnnotatedArgsContext`.
- Finds the kernel binary generated by the `Compile` callback.
- Declares the three refreshable address slots with `AnnotatedKernelArgs(InputAddr{0}, InputAddr{1}, OutputAddr{0})`.
- Sets `kernel_name`, `kernel_bin`, `block_dim`, and args through `AnnotatedKernelLaunchInfo`.
- Calls `ctx.AddLaunch` so GE can generate the corresponding `TaskDef`.

After OM generation, `CustomTaskInfo` consumes `TaskDef.kernel().args()` and `TaskDef.kernel().context().args_format()` directly. It does not call `DeclareLaunchArgs` again during model loading.

## Notes

- `run.sh` uses `--soc_version=Ascend910B1` by default. Adjust it for your hardware if needed.
- This sample demonstrates the standard OM path, not the mobile OMC compatibility path.
- The graph input shape is fixed to `[8192]` float32, matching the sample kernel processing pattern of 1024 elements per block.
- This sample focuses on single-operator single-task declarative address refresh. Multi-task support can be extended by calling `ctx.AddLaunch` multiple times.
