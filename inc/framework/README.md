# OM2 SO 与 Executor C ABI 兼容规则

本文定义 OM2 中 Executor 与 SO 之间 API、数据结构及其使用方式的前后向兼容规则。Executor 通过 `dlopen + dlsym` 按 API 符号名获取 SO 能力；SO 配套 JSON 已分别记录 ABI 兼容版本和构建/发布版本。

## 1. API 保持 C 接口

- Executor 与 SO 双向调用的 API 均使用 C ABI，避免 C++ 名字改编、类布局、STL、模板、异常和 RTTI 成为接口的一部分。
- 导出符号名、调用约定和导出可见性固定。
- SO 内部可以使用 C++ 实现，但异常不得跨 Executor/SO 边界传播；失败通过既有的 C 兼容返回值或输出参数表达。

## 2. 已发布 API 不可删除或修改

- 本规则同时适用于 Executor 调用 SO 的导出 API，以及 SO 回调 Executor 的回调 API。
- 已发布 API 的符号名、函数原型、参数数目和顺序、参数/返回值类型、调用约定、可空性、导出可见性均不可删除或修改。
- Executor 通过 `dlopen + dlsym` 判断新增 API 是否可调用。新增能力只能新增导出符号，不能复用、替换或移除旧符号。
- 已发布 API 的行为语义同样冻结：不得缩小原本接受的合法输入范围，不得改变默认行为、返回码含义、资源释放责任、对象有效期或输出结果含义。
- 状态码、枚举值和 flag 位一经发布，其数值和语义保持不变；新增值只能追加。
- 已发布 API 的线程安全级别、可重入性、调用顺序要求不可收窄。例如，原本可并发调用的 API 不得改为要求外部串行化。
- 回调 API 的触发时机、执行线程、上下文指针含义、回调期间对象有效期和重入约束，均属于冻结的行为语义。
- 字符串的编码、是否以 `\0` 结束、长度字段是否包含终止符、内存归属与有效期，均属于冻结的 API 语义。

## 3. 新 API 的参数扩展

- 新 API 的函数位置参数保持最小且稳定。
- 存在扩展需求的一组参数，使用带 `struct_size` 的独立 Input/Output 结构体，不通过持续增加函数位置参数扩展。
- Input 和 Output 使用不同结构体、不同参数：Input 由 Executor 填写、SO 读取；Output 由 Executor 提供存储、SO 填写。
- 只有稳定的简单标量参数时，不强制为其额外设计结构体。

## 4. 跨 ABI 的数值类型

- 新增公开 API 参数和公开结构体字段使用宽度明确的数值类型。
- 已发布字段或参数的类型不可修改。
- 状态码、枚举和 flag 等跨边界数值，其取值定义与语义随 API 一并冻结，不能改变既有值的解释。

## 5. 跨边界内存、对象与 Handle

- 所有跨边界内存、对象和 handle 均须明确创建方、释放方和有效期；这些约定一经发布不可改变。
- 一侧创建的资源，不允许由另一侧直接以其自身的分配器释放；应由创建侧提供对应的释放或销毁 API。
- 可演进对象只通过不透明 handle 暴露，不对外暴露内部对象布局。
- handle 的有效/失效时机、销毁后的行为、SO 卸载前的资源清理要求，均属于 API 行为语义。

## 6. 可扩展公开结构体

- 每个需要后续扩展的跨 ABI 公开结构体都使用 `struct_size`。
- `struct_size` 表示调用方本次提供的结构体字节范围；调用前由调用方正确初始化，调用过程中 Executor 和 SO 均不得修改。
- SO 读取 Input、写入 Output 时，均只能访问 `struct_size` 覆盖的字段范围。
- `struct_size` 不表达实际结果大小、元素数量或所需缓冲区大小；这些信息使用独立字段。
- 结构体及其已发布成员不得删除、改名、改类型、调整顺序、改变含义或改变对齐要求。
- 新字段只能追加在结构体末尾。新版结构体的 `sizeof` 必须严格大于旧版，且第一个新增字段的 `offsetof` 必须不小于旧版 `sizeof`。
- 新增字段必须具备保持旧行为的默认值。旧结构体缺少该字段时，不能因此被拒绝。
- 若新能力没有可保持旧行为的默认值，不得直接给旧结构体追加必填字段；应新增 API 或新的参数结构体。
- 初始化语法糖只是推荐机制；规则只要求调用前 `struct_size` 与实际提供的内存范围一致，不限定定义时初始化、后续初始化或堆分配等写法。

### 字段语义有效性

`struct_size` 只能判断字段是否在调用方提供的内存范围内，不能判断调用方是否有意设置该字段，更不能等同于功能已开启。

- 每个控制可选功能或可选配置的字段，必须能区分“字段未提供/未指定”“字段已提供但功能关闭或采用默认行为”“字段已提供且功能开启”。
- 不得以字段是否非零、或 `struct_size` 是否覆盖该字段，隐式推断字段具有业务意义。
- 根据字段语义，可使用显式启用字段、独立有效位，或包含 `UNSPECIFIED`、`DISABLED`、`ENABLED` 等状态的模式字段表达该区分。

## 7. 结构体嵌套

- 可扩展结构体通常应通过指针嵌套，内层结构体独立按其 `struct_size` 演进；不得让其扩展导致已发布外层成员偏移漂移。
- 若聚合类型（例如联合体）在跨 ABI 前已经由指针间接，且该聚合类型本身不按值跨 ABI 传递，则其按值成员可以扩展；必须保证既有成员前缀布局不变，并且不移动任何已发布外层成员。
- 只有承诺布局永久冻结、永不增加成员且不包含可扩展结构体的内层结构体，才可无条件按值嵌套。

## 8. 显式 ABI 填充与布局稳定

- 公开 ABI 结构体不得存在未命名的天然对齐空洞。
- 对齐填充统一使用 `uint8_t abi_pad_<序号>[<字节数>]` 显式定义；即使只有一个字节也使用数组形式。
- `abi_pad_N` 是冻结的物理布局填充，不承载业务数据。它可以随整体结构体初始化被置零，但 SO 不得读取、写入或基于其内容做逻辑判断。
- 已发布的 `abi_pad_N` 不得启用、复用、删除、缩短、改类型、移动或改名；新增字段必须追加在它之后。
- 新增字段后若需新的填充，可以新增新的 `abi_pad_N`，但不得占用旧版填充空间。
- 公开 ABI 结构体的 packing/alignment 策略不得变化，也不得因 `#pragma pack`、编译选项或局部属性导致布局漂移。
